# PG-Power 开发日志

## 项目概述

PG-Power 是一个基于 GPIB 接口的电源实时采集工具，使用 PyQt5 构建 GUI，PyQtGraph 绘制实时曲线。

## 开发记录

### 2026-06-11：初始改造与打包

#### 1. 问题：ni4882.dll 加载失败导致程序崩溃退出

**现象：**
程序在启动时尝试加载 `ni4882.dll`，由于开发机未安装 NI-488.2 驱动（缺少 `nipalu.dll`、`ni488config.dll` 等依赖），`ctypes.WinDLL()` 抛出异常，程序执行 `sys.exit(1)` 直接退出，GUI 无法显示。

**解决方案：**
- 将 DLL 加载从致命错误改为非致命警告
- 引入全局标记 `GPIB_AVAILABLE` 统一管控 GPIB 功能
- 所有 GPIB 操作函数（`gpib_open`、`gpib_close`、`gpib_send_cmd`、`gpib_query`）增加 `GPIB_AVAILABLE` 前置检查
- DLL 加载失败时：GUI 正常启动，所有 GPIB 按钮自动禁用并显示悬浮提示
- 弹窗警告用户需要安装 NI-488.2 驱动

#### 2. 问题：Qt 平台插件找不到（No Qt platform plugin）

**现象：**
首次运行显示 `qt.qpa.plugin: Could not find the Qt platform plugin "windows"`。

**原因：**
PyQt5 需要 `qwindows.dll` 平台插件，但 `QT_QPA_PLATFORM_PLUGIN_PATH` 环境变量未正确设置。开发模式下插件在 `venv/Lib/site-packages/PyQt5/Qt5/plugins/platforms/`。

**解决方案：**
- 在导入 PyQt5 之前，检测当前运行模式（开发/打包）
- 开发模式：设置 `QT_QPA_PLATFORM_PLUGIN_PATH` 指向 venv 内的插件目录
- 将 Qt bin 目录也加入 `PATH` 确保依赖 DLL 可加载

```python
if getattr(sys, 'frozen', False):
    _base = sys._MEIPASS  # PyInstaller 打包模式
else:
    _base = os.path.dirname(os.path.abspath(__file__))  # 开发模式
_qt_platforms = os.path.join(_base, "PyQt5", "Qt5", "plugins", "platforms")
if os.path.isdir(_qt_platforms):
    os.environ["QT_QPA_PLATFORM_PLUGIN_PATH"] = _qt_platforms
```

#### 3. 问题：PyInstaller 打包时中文路径编码错误

**现象：**
打包时 PyInstaller 的 Qt 钩子报错：`Qt plugin directory 'D:/?????/?????/P55/????/PG-Power/...' does not exist!`

**原因：**
项目路径包含中文字符（`D:\工作文件夹\宠物定位器\P55\测试工具\PG-Power`），PyInstaller 的 `hook-PyQt5.QtWidgets.py` 通过隔离子进程调用 `QLibraryInfo.location()` 获取插件路径，返回的中文字符在序列化过程中编码丢失变为 `?`。

**解决方案（绕开方案）：**
- 创建自定义 PyInstaller 钩子目录 `pyi_hooks/`
- 覆盖 `hook-PyQt5.py`、`hook-PyQt5.QtWidgets.py`、`hook-PyQt5.QtCore.py`、`hook-PyQt5.QtGui.py`、`hook-pyqtgraph.py`
- 自定义钩子返回空 `binaries` 和 `datas`，避免触发自动插件检测
- 在自定义 spec 文件中手动收集 Qt 二进制和插件文件：

```python
# 手动收集 Qt bin 下的 .dll
for f in os.listdir(bin_dir):
    if f.lower().endswith('.dll'):
        qt_binaries.append((os.path.join(bin_dir, f), 'PyQt5/Qt5/bin'))

# 手动收集 plugins 下所有文件
for root, dirs, files in os.walk(plugins_dir):
    for f in files:
        src = os.path.join(root, f)
        rel = os.path.relpath(root, os.path.dirname(pyqt5_dir))
        qt_datas.append((src, rel))
```

#### 4. 问题：打包 EXE 后 Qt 平台插件找不到

**现象：**
目标电脑运行 `PG-Power.exe` 报错：`This application failed to start because no Qt platform plugin could be initialized.`

**原因：**
PyInstaller 单文件模式下，文件解压到 `sys._MEIPASS` 临时目录，但 `QT_QPA_PLATFORM_PLUGIN_PATH` 未正确指向该目录下的插件位置。

**解决方案：**
在 `main.py` 中统一处理开发模式和打包模式的插件路径：

```python
if getattr(sys, 'frozen', False):
    _base = sys._MEIPASS
else:
    _base = os.path.dirname(os.path.abspath(__file__))
```

同时修正 spec 文件中插件目标路径，保持 `PyQt5/` 前缀与解压目录结构一致。

### 2026-10-09：在线更新机制全面修复（v2.0.14 → v2.0.27）+ 仓库历史瘦身

#### 一、在线更新修复（已验证可用）

**问题演进：** 从 v2.0.12 升级 v2.0.13 起，更新下载成功但新版本无法启动 / 替换失败 / 反复弹错，历经多轮修复最终在 v2.0.27 全部解决。

**根因与修复：**

1. **批处理脚本编码冲突**：更新脚本为 GBK 编码却带 `chcp 65001`，中文路径乱码 → 改为纯 PowerShell 脚本（`pg_power_update.ps1`），避免 bat/VBS 的编码与引号嵌套问题
2. **守护线程随主进程被杀**：Python 线程做替换时主进程退出即被终止 → 改用 `wscript.exe` 启动完全独立的 PowerShell 进程执行替换
3. **模态弹窗阻塞事件循环**：GPIB 驱动警告在 `__init__`（show() 之前）模态弹出，嵌套循环触发 3 秒自动检查定时器，更新对话框先于 GUI 出现；且新进程唯一窗口标题为"提示"，被更新脚本误判为错误窗口杀掉 → 警告改为主窗口 show() 后 800ms `QTimer.singleShot` 延迟弹出
4. **窗口检测不可靠**：`Get-Process MainWindowTitle` 只能看到一个窗口 → 用 C# `Add-Type` P/Invoke `EnumWindows` 枚举新进程**全部可见窗口标题**，任一匹配 `PG-Power |` 即视为成功；窗口标题恰为 `Error`（PyInstaller DLL 对话框）时快速失败（errwin），按 5/10/20s 退避重试 4 次（杀毒软件实时扫描可能短暂阻塞新 exe 首次执行）
5. **并发更新脚本互杀**：多实例同时改日志、互相 kill 对方拉起的进程 → ps1 加单实例锁（`CreateNew` + 持有者 PID，PID 已死或锁龄 > 15 分钟可恢复）
6. **替换假成功**：`Move-Item` 无 `-ErrorAction Stop` 静默失败仍继续启动旧文件 → 显式 `$moved` 标志，替换失败则跳过启动；三级回退 `Move-Item -Force` → `Copy-Item` → `Remove-Item + Copy-Item`；旧进程 60 秒不退强杀
7. **新 exe 落盘命名**：新版本以其**新文件名**落在当前 exe 目录，删除旧名文件后启动新路径（放置失败时原地覆盖兜底）
8. **其他**：更新防重入（下载/替换期间忽略重复触发）；`check_update` 无更新提示报**所有源中的最高版本**（CDN 回源缓存会给出过期版本误导用户）；GitCode contents API 单文件可能 404 数分钟 → 从父目录列表取 `download_url`
9. **下载体验**：`QProgressDialog` 实时进度（百分比 + MB）；确认框三个按钮「立即下载 / 在浏览器下载 / 稍后再说」+ 可点击下载链接；启动后 3 秒自动检查更新且不阻塞 UI

**下载源**：GitCode blobs（raw.gitcode.com/blobs/<sha>/），实测 5.9 MB/s，70MB 约 12 秒。

#### 二、仓库历史瘦身（2.4 GiB → 81.8 MiB）

**背景**：历史中堆积 27 个版本 exe（仓库 2.4 GiB，远超 GitCode 1 GiB 限额），且提交 `06334ee` 误将 exe 内容提交为 73.8 MB 的 `main.py` 垃圾 blob。

**执行：**

1. 备份 `releases/` 全部 exe 到仓库外目录
2. `git filter-repo --force --invert-paths --paths-from-file`（规则 `regex:^(?!.*PG-Power_v2\.0\.27\.exe).*\.exe$`）清除历史中除 `PG-Power_v2.0.27.exe` 外全部 exe —— 2.4 GiB → 152 MB pack
3. 垃圾 `main.py` blob（`5acb2fa...`，73.8 MB）清理：本机杀毒（Defender + 火绒）锁定 fast-import pack 文件，`filter-repo + blob_callback` 反复报 `cannot truncate pack to skip duplicate: Permission denied`，最终改用 **`git filter-branch --index-filter`**（`ls-tree` 匹配垃圾 SHA 后 `update-index --cacheinfo` 换成注释 blob，完全绕开 fast-import）→ pack 降至 **81.8 MiB**
4. 清理 `refs/original` + `reflog expire` + `gc --prune=now`，`git fsck` 干净
5. 重写后的 master（`1d41495`）+ 全部 27 个 tag force push 至 GitCode（SSH 推大包被断连，改 HTTPS + token）和 GitHub

**关键验证：**

- Git blob SHA 基于内容 → 保留 exe 的 SHA `1ae20ae9...` 不变，`version.json` 的 `exe_url`（raw.gitcode.com/blobs/<sha>/...）**实测 Range GET 返回 MZ 头，下载链接有效**
- 历史中 26 个旧 exe blob 与 73.8 MB 垃圾 main.py 均已消失
- 双仓库 master/tags 与本地完全一致

**遗留待办**：GitCode 网页端 项目设置 → Project Management → **Compact**（手动执行后服务端旧对象才真正释放，当前仍显示超限警告）；其他机器需重新克隆。
